# 서버 데이터는 값이 아니라 캐시다

## 1. 나는 이 라이브러리를 이해하지 못한 채로 받아들였다

모먼트 커피라는 카페 주문 앱의 프론트엔드 설계를 정리하면서 ADR을 작성했다. 기술 스택을 고르는 과정에서 AI에게 요구사항 명세서를 주고 각 결정의 근거를 함께 정리했는데, 서버 상태 항목에 다음이 올라왔다.

> **D6. 서버 상태 — TanStack Query v5**
>
> - **C8 (주문 상태 갱신):** `refetchInterval`로 주문 상태 화면에서만 폴링. 초기값 5초. 상태가 `수령`이면 폴링 중단.
> - **C7 (로딩 상태 표시):** `isPending`/`isError`가 1급 상태로 제공되어 요구가 구현이 아니라 사용이 된다.
> - **FR-103 (검색 200ms):** 메뉴 목록은 이미 캐시에 있으므로 서버 요청 없이 클라이언트 필터링.

명세서에는 이런 요구가 있었다. 주문 상태가 접수 → 제조중 → 완료 → 수령으로 **매장 처리에 따라** 바뀌고, 검색 결과는 200ms 안에 나와야 하며, 대기 중에는 로딩 상태를 보여줘야 한다. AI는 이 세 요구를 근거로 라이브러리를 하나 제안한 것이다.

납득할 만한 근거였다. 그런데 나는 그 라이브러리가 **무엇을 하는 물건인지 몰랐다.** 이름에 Query가 들어가니 데이터를 가져오는 도구겠거니 했고, 코드 예시를 보고는 이렇게 짐작했다.

```ts
const { data, isPending, isError } = useQuery({ ... });
```

> 서버에서 받은 데이터를 DTO 따로 만들 필요 없이 바로 구조분해할 수 있게 해주는 라이브러리인가?

틀렸다. 저기서 구조분해되는 `{ data, isPending, isError }`는 **서버가 준 데이터가 아니라 TanStack Query가 만든 결과 객체**다. `data`는 내가 넘긴 `queryFn`이 반환한 값 그대로이고, 라이브러리는 응답을 열어보지도 변환하지도 않는다.

이 글은 그 오해에서 출발해서, 이 라이브러리가 실제로 무엇을 해결했는지 원리까지 따라간 기록이다.

> [!note] 이 글의 범위
> 모먼트 커피는 아직 설계 문서 단계이고 구현 전이다. 따라서 이 글은 **동작하는 코드로 검증한 결과가 아니라 개념을 정리한 노트**다. 벤치마크나 실측치는 없다.

## 2. 손으로 쓰던 시절의 문제

비교 기준을 먼저 세우자. TanStack Query 없이 React에서 API를 호출하면 보통 이렇게 쓴다.

```ts
function MenuList({ storeId }: { storeId: string }) {
  const [data, setData] = useState<Menu[] | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    let cancelled = false;
    setLoading(true);

    api.getMenus(storeId)
      .then(d => { if (!cancelled) setData(d); })
      .catch(e => { if (!cancelled) setError(e); })
      .finally(() => { if (!cancelled) setLoading(false); });

    return () => { cancelled = true; };
  }, [storeId]);

  // ...
}
```

동작은 한다. 문제는 이 코드가 **화면 수만큼 반복된다**는 것과, 반복될 때마다 아래 결함이 함께 복제된다는 것이다.

### 2.1 세 개의 상태를 손으로 동기화한다

`data` · `loading` · `error`는 사실 하나의 상태 기계다. 로딩 중이면 에러가 없어야 하고, 에러가 있으면 로딩이 끝나 있어야 한다. 그런데 위 코드는 이 셋을 **독립된 `useState` 세 개**로 두고 순서를 손으로 맞춘다. `finally`를 빠뜨리면 로딩이 영원히 끝나지 않고, `setError(null)`을 재요청 시점에 안 넣으면 이전 에러가 남는다.

### 2.2 경쟁 조건이 조용히 숨는다

`storeId`가 A에서 B로 빠르게 바뀌면 요청도 두 개가 나간다. 그런데 응답 순서는 보장되지 않는다.

```
요청 A ─────────────────────────> 응답 A 도착 (늦음)
요청 B ──────> 응답 B 도착

setData(B)  →  setData(A)   결과: 화면은 B인데 데이터는 A
```

위 코드가 `cancelled` 플래그를 들고 있는 이유가 이것이다. 그런데 이 방어는 **매번 손으로 써야 하고, 빠뜨려도 대부분의 경우 잘 동작한다.** 네트워크가 빠른 개발 환경에서는 재현되지 않다가 실제 사용자 환경에서만 가끔 틀린다. 가장 잡기 싫은 종류의 버그다.

### 2.3 캐시가 없다

같은 메뉴 목록을 장바구니 화면과 메뉴 화면이 모두 필요로 하면 요청이 두 번 나간다. 탭을 옮겼다 돌아오면 컴포넌트가 다시 마운트되면서 또 나간다. 사용자 입장에서는 이미 봤던 화면인데 다시 스피너를 본다.

명세의 "검색 결과 200ms 이내"는 이 상태에서는 네트워크 문제가 된다. 캐시가 있다면 애초에 서버를 가지 않으므로 **렌더 문제로 축소**되는데, 그 차이가 여기서 갈린다.

### 2.4 무효화의 근거가 코드 어디에도 없다

결제를 하면 리워드 잔액이 바뀐다. 그런데 위 구조에서는 "리워드 화면의 `data`가 지금 낡았다"는 사실을 **아는 코드가 존재하지 않는다.** 결제 화면과 리워드 화면은 서로를 모르기 때문이다.

그래서 보통 두 가지 회피책 중 하나로 간다. 리워드 화면에 들어갈 때마다 무조건 다시 요청하거나(2.3의 문제가 커짐), 전역 store에 응답을 올려서 결제 시 직접 갱신하거나. 후자를 택하면 다음 절의 문제로 들어간다.

### 2.5 전역 store에 올리면 더 큰 문제가 된다

Redux 같은 클라이언트 상태 저장소에 서버 응답을 넣어 공유하면 2.3과 2.4는 일단 풀린다. 대신 이런 질문이 생긴다.

- 이 데이터는 **언제 것인가?** 10초 전 것인가 10분 전 것인가
- 다시 가져와야 하는가? 그 판단은 누가 하는가
- 두 화면이 서로 다른 시점의 데이터를 보고 있으면 어떻게 하는가
- 사용자가 탭을 떠났다 돌아왔을 때는?

이 질문들에 답이 없는 이유가 있다. 애초에 잘못된 자리에 넣었기 때문이다.

## 3. 문제의 뿌리 — 서버 데이터를 클라이언트 상태처럼 다뤘다

2장의 결함들은 각각 별개의 실수처럼 보이지만 원인은 하나다. **서버에서 온 데이터를 내가 소유한 값처럼 취급한 것.**

두 가지를 나란히 놓아 보면 성질이 다르다는 게 드러난다.

| | 장바구니 시트가 열렸는가 | 메뉴 목록 |
|---|---|---|
| 소유자 | 나 (클라이언트) | 서버 |
| 내 값의 정확성 | **항상 정확하다** | 언제든 낡았을 수 있다 |
| 바뀌는 계기 | 내가 바꿀 때만 | 내가 모르는 사이에도 |
| 성질 | 값 | **복사본** |

장바구니 시트의 열림 여부는 내가 유일한 소유자다. 내가 `true`로 뒀으면 그건 참이다. 확인할 필요가 없다.

메뉴 목록은 다르다. 원본은 서버에 있고 내가 가진 건 **어느 시점의 스냅샷**이다. 사장님이 방금 품절 처리를 했을 수도 있다. 내가 아무것도 하지 않아도 내 값이 틀려질 수 있다.

즉 서버 데이터에는 **"언제 것인가"라는 시간 차원**이 붙는다. `useState`에는 그런 차원이 없다. 그래서 2장의 문제들이 전부 "직접 관리"로 떨어진 것이다. 도구에 없는 개념을 사람이 매번 손으로 메우고 있었다.

> [!tip] 이 글의 한 문장
> **서버 데이터는 값이 아니라 권위 없는 복사본이다.** 이걸 인정하는 순간 필요한 기능들이 따라 나온다.

### 3.1 "임시 데이터에 유효기간을 붙인다"와는 다르다

처음에 나는 이걸 TTL 캐시로 이해했다. 임시 데이터니까 유효기간을 붙이고 지나면 버린다는 식으로. 그런데 두 군데가 어긋난다.

**첫째, "임시"가 아니다.** 오래 들고 있는다. 문제는 보관 기간이 아니라 **권위가 없다**는 것이다.

**둘째, 만료돼도 버리지 않는다.** TTL 캐시는 만료되면 폐기하고 다음 요청은 빈손에서 시작한다. 그러면 만료 순간 화면이 스피너로 돌아간다. TanStack Query의 `staleTime`은 다르다.

```
staleTime 경과
  → "낡았다"고 표시만 한다
  → 화면에는 낡은 데이터를 그대로 즉시 보여준다
  → 동시에 백그라운드로 다시 가져온다
  → 도착하면 조용히 교체한다
```

이 패턴을 **stale-while-revalidate**라고 부른다. 사용자는 화면이 비는 걸 보지 않는다. 명세의 "화면 전환 1초 이내"를 만족시키는 게 정확히 이 동작이다.

그래서 시계가 두 개다.

| | 의미 | 지나면 |
|---|---|---|
| `staleTime` | 신선도 | **버리지 않는다.** 다음 기회에 재검증 |
| `gcTime` | 메모리 수명 | 아무도 구독하지 않을 때 캐시에서 제거 |

**셋째, 시간만으로는 부족하다.** 결제를 하면 리워드 잔액은 1초가 지났든 안 지났든 **그 순간** 낡는다. 유효기간이라는 모델로는 이걸 표현할 수 없다. 그래서 `invalidateQueries`가 따로 있다 — 시간이 아니라 **사건**으로 낡히는 통로다.

정리하면 이렇게 된다.

> 서버 데이터는 권위 없는 복사본이다. 그래서 **신선도**라는 상태를 갖고, **시간이나 사건**으로 낡으며, 낡아도 **버리지 않고 보여주면서 뒤에서 맞춘다.**

## 4. 2장의 문제를 어떻게 풀었나

3장의 관점을 코드로 옮기면 두 개의 도구가 나온다. **캐시에 주소를 주는 것**(`queryKey`)과 **캐시에 수명을 주는 것**(`staleTime`)이다. 2장의 결함이 여기서 어떻게 사라지는지 하나씩 본다.

```ts
const { data, isPending, isError } = useQuery({
  queryKey: queryKeys.menus(tenantKey, storeId),
  queryFn: () => api.getMenus(storeId),
  staleTime: 5 * 60 * 1000,
});
```

### 4.1 상태 기계를 라이브러리가 소유한다 (2.1)

`isPending` · `isError` · `data`는 하나의 상태 기계에서 파생된다. 내가 셋을 동기화할 일이 없다. 요구가 구현이 아니라 **사용**이 되는 지점이 여기다.

### 4.2 경쟁 조건이 구조적으로 사라진다 (2.2)

`storeId`가 바뀌면 `queryKey`가 바뀐다. 키가 다르면 **다른 캐시 항목**이므로 A의 응답이 B의 자리에 쓰일 길이 없다. `cancelled` 플래그를 손으로 쓰던 방어가 키 설계로 흡수된다.

이게 `queryKey`의 첫 번째 역할이다. 키는 인자가 아니라 **주소**다.

### 4.3 같은 키를 보는 화면은 같은 데이터를 본다 (2.3)

`queryKey`가 같으면 캐시 항목이 같다. 그래서

- 두 컴포넌트가 동시에 마운트돼도 요청은 **한 번** 나간다 (dedup)
- 탭을 옮겼다 돌아오면 캐시에 있던 값을 **즉시** 그린다
- 메뉴가 이미 캐시에 있으니 검색은 서버를 가지 않는다 → 200ms가 네트워크 문제에서 렌더 문제로 축소

### 4.4 무효화에 통로가 생긴다 (2.4, 2.5)

```ts
// 결제 완료 시점
queryClient.invalidateQueries({ queryKey: ["tenant", tenantKey, "reward"] });
```

"이 주소의 데이터는 낡았다"고 **선언**하면, 그 키를 구독 중인 화면이 알아서 갱신된다. 결제 화면이 리워드 화면을 알 필요가 없다. 둘은 서로가 아니라 **키를 통해** 만난다.

2.5에서 답이 없던 질문들도 여기서 풀린다. "언제 것인가"는 `dataUpdatedAt`이 들고 있고, "다시 가져와야 하는가"는 `staleTime`이 판단하며, "두 화면이 다른 시점을 보는" 일은 같은 캐시 항목을 공유하므로 애초에 생기지 않는다.

### 4.5 사고방식이 명령형에서 선언형으로 바뀐다

이게 결과적으로 가장 큰 변화다.

| | 쓰는 것 | 언제 가져올지 정하는 주체 |
|---|---|---|
| 이전 | "지금 가져와서 상태에 넣어라" | 나 (`useEffect` 의존성 배열) |
| 이후 | "이 화면은 이 키의 데이터가 필요하다" | **라이브러리** |

`refetchInterval: 5000` 한 줄로 주문 상태 폴링이 끝나는 것도 같은 이유다. 나는 **무엇이 필요한지만** 쓰고, 언제 가져올지는 캐시의 신선도 규칙이 정한다.

### 4.6 반대로, 해주지 않는 것

관점을 명확히 하려면 경계도 그어야 한다.

- **변환하지 않는다.** `data`는 `queryFn`의 반환값 그대로다. DTO를 화면용 모델로 바꾸는 일은 여전히 내 몫이다
- **런타임 타입을 보장하지 않는다.** `useQuery<Menu[]>`의 제네릭은 컴파일 타임 단언일 뿐이다. 서버가 다른 걸 보내도 아무 일도 일어나지 않는다
- **클라이언트 상태를 다루지 않는다.** 장바구니는 서버에 원본이 없으므로 낡을 수가 없다. 무효화 대상이 아니라 그냥 초기화하면 되는 값이다

그래서 모먼트 커피 설계에서는 세 축이 따로 서 있다.

| 질문 | 담당 |
|---|---|
| 언제 가져오고, 어디 캐시하고, 언제 다시 가져오나 | TanStack Query |
| 받은 게 진짜 그 모양이 맞나 (런타임) | Zod — 금액·상태 응답에만 |
| 서버 모양 → 화면 모양 변환 | `model/` 순수 함수 |

## 5. 원리 — 무엇이 싱글톤이고 무엇이 아닌가

여기서 내가 또 한 번 틀렸다. 캐시가 공유된다는 걸 알고 나서 이렇게 생각했다.

> `useQuery`가 반환하는 건 싱글톤 데이터를 들고 있는 싱글톤 객체겠구나

아니다. 싱글톤인 층과 아닌 층이 나뉘어 있고, 그 경계를 아는 게 이 라이브러리를 이해하는 마지막 조각이었다.

### 5.1 객체 그래프

```
QueryClient                       ← 앱당 1개 (싱글톤)
 └ QueryCache                     ← 앱당 1개 (싱글톤)
    └ Query                       ← queryKey 당 1개 (공유됨)
       │  · data, error, status
       │  · dataUpdatedAt
       │  · 진행 중인 promise
       │  └ observers[]           ← 자신을 구독 중인 옵저버 목록
       │
       ├── QueryObserver          ← useQuery 호출 당 1개
       │      └ result 객체       ← 렌더마다 새로 생성  ⟵ useQuery의 반환값
       └── QueryObserver
              └ result 객체
```

정리하면 이렇다.

| 층 | 개수 | 공유되는가 |
|---|---|---|
| `QueryClient` / `QueryCache` | 앱당 1개 | 싱글톤 |
| `Query` | **queryKey 당 1개** | 같은 키를 쓰는 컴포넌트끼리 공유 |
| `QueryObserver` | `useQuery` 호출 당 1개 | 공유 안 됨 |
| `useQuery`의 반환값 | 렌더마다 새로 | 공유 안 됨 |

**데이터는 공유되지만 결과 객체는 공유되지 않는다.** 내가 헷갈린 지점이 정확히 여기였다.

### 5.2 저장 위치

캐시는 React 트리 **바깥**의 평범한 자바스크립트 객체에 있다.

```ts
const queryClient = new QueryClient();   // ← 캐시가 여기 산다

<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>
```

여기에 구조적으로 중요한 디테일이 하나 있다. **`QueryClientProvider`가 Context로 내려주는 건 클라이언트 인스턴스뿐이고, 데이터는 Context를 타지 않는다.**

Context에 데이터를 직접 넣으면 값이 바뀔 때 구독 트리 전체가 리렌더된다. 이건 Context API를 상태 공유에 쓸 때 마주치는 고전적인 문제다. TanStack Query는 Context로 **주소만** 내려주고, 각 `useQuery`가 자기 키를 개별 구독하는 방식으로 이 함정을 구조적으로 피한다. 메뉴 캐시가 갱신돼도 리워드 화면은 리렌더되지 않는다.

### 5.3 옵저버가 층으로 분리되어 있어서 가능해지는 것

`Query`(공유)와 `QueryObserver`(개별)가 나뉜 덕에, 같은 데이터를 보면서도 컴포넌트마다 다르게 굴 수 있다.

```ts
// 화면 A — 전체 목록이 필요하다
const { data } = useQuery({ queryKey: k, queryFn: f });

// 화면 B — 개수만 필요하다. 같은 캐시를 보지만 다른 모양을 받는다
const { data: count } = useQuery({
  queryKey: k,
  queryFn: f,
  select: (menus) => menus.length,
});
```

`staleTime` · `enabled` · `refetchInterval` 같은 옵션도 옵저버 단위다. 그래서 **주문 상태 화면에서만 폴링**하고 다른 화면은 안 하는 게 성립한다. 폴링은 데이터의 속성이 아니라 그 화면이 데이터를 보는 방식의 속성이기 때문이다.

### 5.4 구조적 공유

재요청 결과가 이전과 **깊은 값이 같으면** 이전 참조를 그대로 유지한다. 참조가 안 바뀌므로 `React.memo`나 `useMemo` 의존성이 걸린 하위 트리가 리렌더되지 않는다.

낡음을 자주 확인하는 설계는 재검증도 자주 하게 되는데, 그때마다 새 객체를 만들면 화면 전체가 흔들린다. 이 최적화는 stale-while-revalidate를 실용적으로 쓰기 위한 전제에 가깝다.

### 5.5 새로고침하면 사라진다

캐시는 메모리에 있으므로 새로고침하면 비워진다. 그런데 이건 결함이 아니라 3장의 관점에서 나온 **당연한 귀결**이다. 원본이 서버에 있으니 굳이 디스크에 붙들 이유가 없다. 다시 가져오면 그만이고, 오히려 그게 더 정확하다.

모먼트 커피 설계에서 상태별 영속 정책이 갈린 것도 같은 이유다.

| 상태 | 소유 | 영속 |
|---|---|---|
| 메뉴 · 매장 · 쿠폰 · 리워드 · 주문 | TanStack Query | **메모리** (서버가 원본) |
| 장바구니 · 선택 매장 | Zustand + persist | **localStorage** (여기가 원본) |

## 6. 남은 것

이해가 끝난 자리에서 다음 질문이 생겼다. 아직 답을 못 냈다.

- **`session` 쿼리의 경계.** 결제 완료 시 무효화 대상을 정리하다가 막혔다. `session`이 인증 정보만 담으면 결제로 낡지 않는데, 사용자 프로필을 반환하면서 포인트 잔액을 물고 오면 낡는다. **키가 무엇을 담는지가 모호하면 무효화 범위도 모호해진다.** 캐시에 주소를 준다는 건 주소의 경계를 정하는 일이기도 했다
- **`staleTime` 값을 무엇을 근거로 정하는가.** 메뉴는 5분이 적당해 보이지만 그 5분의 근거가 감이다
- 실제 구현에서 낙관적 업데이트를 썼을 때 롤백 처리가 어디까지 손이 가는지

## 7. 정리

이 라이브러리를 이해하는 데 걸린 시간의 대부분은 API를 익히는 데 쓰이지 않았다. **서버 데이터를 무엇으로 취급할 것인가**라는 관점을 바꾸는 데 쓰였다.

값으로 보면 캐시·무효화·재검증은 전부 부가 기능처럼 보인다. 권위 없는 복사본으로 보면 그것들은 **복사본을 다루려면 반드시 있어야 하는 것들**이 된다. 같은 기능 목록인데 순서가 반대다.

AI가 설계 문서에서 라이브러리를 추천했을 때 나는 근거는 읽었지만 관점은 못 읽었다. 근거는 요구사항과 기능을 연결한 문장이었고, 관점은 그 아래 깔려 있어서 문서에 안 적혀 있었다. **추천을 받아들이는 것과 이해하는 것은 다른 일**이라는 걸 이번에 배웠다.
